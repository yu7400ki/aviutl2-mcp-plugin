# 設定項目の面の生成器

`crates/plugin/data/effect_item_facets.json` を、起動中の AviUtl2 への書き込み
検証で起こす。plugin はこの JSON を `include_str!` でバイナリへ取り込む。

**面**とは、設定項目 1 件について表が述べることである。いまは 2 つある。

| 面 | 内容 | 対象の種別 |
|---|---|---|
| `choices` | 選択肢の候補 | `select` / `combo` / `mask` / `figure` |
| `range` | 値域（`min` / `max`）と小数桁（`decimals`） | `integer` / `number` |

**どちらも SDK からは取れない。** 設定項目の列挙がコールバックへ渡すのは名前と
種別だけであり、選択肢を返す関数も値域を返す関数もヘッダーに存在しない。ホストは
持っているが我々へ渡す口が無いため、**書き込みの成否と、ホストが倒した値そのものを
判定に使う。**

生成器はワークスペースの外にある。`Cargo.toml` の `members` は `crates/*` だけを
指すため、**このディレクトリは製品のビルドにも lint にも関与しない。** 新しい版の
AviUtl2 が出たときに 1 度走らせ、出力をコミットする。

**このディレクトリには生成器が 2 つある。** 以下は `generate.mjs` について述べる。
もう 1 つは[移動方法の可否の生成器](#移動方法の可否の生成器)であり、書き出す先も
測るものも違う。**走らせる規模が桁で違うため、入口を分けてある**——効果の走査は
3 分・書き込み 2 万回台であり、あちらは十数件・数十回で終わる。混ぜると、片方の
ために全部を回すことになる。

## 前提

- **AviUtl2 が起動していること。** MCP plugin が読み込まれた状態で 1 つだけ立てる。
- **空のプロジェクトが開いていること。** 生成器はスクラッチのオブジェクトを 1 つずつ
  作っては消し、候補を総当たりで書き込み、値域を探る値で叩く。**既存のオブジェクトには
  触れないが、プロジェクトは編集済みになる。** 保存しないこと。
  **空であることは作法ではなく完走の条件である**——[書き込み 1 回の費用](#書き込み-1-回の費用は-timeline-の中身が決める)を参照。
- **走査は 3 分ほど掛かる。** 効果 147 件・(効果, 項目) 604 組・書き込み 2 万回台が
  目安である。進み方は `[束の番号/束の総数] 作り方 から N 組` の行で追える。
- **`target/release` か `target/debug` に `aviutl2-mcp-server.exe` があること。**
  release を先に探す。
- **`[Effect]` 節を持つ言語ファイルがあること。** 候補の在庫の供給源である。作者が
  配布する英語言語ファイルがこれにあたる。既定では開発用ディレクトリの
  `data\Language`、次に `%ProgramData%\aviutl2\Language` を見て、`[Effect]` 節を
  持つ最初の `*.aul2` を採る。
- **Node.js。** 標準ライブラリだけで動く。依存パッケージは無い。

## 使い方

```
node tools/effect-choices/generate.mjs
```

| 引数 | 既定 | 内容 |
|---|---|---|
| `--language <path>` | 開発用ディレクトリ → `%ProgramData%` の走査 | 在庫を読む言語ファイル |
| `--out <path>` | `crates/plugin/data/effect_item_facets.json` | 書き出し先 |
| `--server <path>` | `target/release` → `target/debug` | MCP サーバーの実行ファイル |
| `--max-writes <n>` | 130000 | 書き込みの総回数の上限 |

## 候補をどう起こすか

言語ファイルの `[Effect]` 節には効果名・項目名・選択肢ラベルが**重複排除された
まま平坦に**並ぶ。どれが選択肢かも、どの項目のものかも書かれていない。そこで
**書き込みの成否そのものを判定に使う**——選択肢に無い値を書くと
`item_value_not_applied` で失敗し、**状態は変わらない。**

1. 全種別の効果を列挙し、対象の設定項目を集める
2. 各効果を載せたオブジェクトの作り方を実機で決める。効果から直接作れないものは、
   他の効果から作ったオブジェクトに同伴するかを見る（`テキスト` のオブジェクトには
   `標準描画` が、`フレームバッファ` には `基本出力` が付いてくる）
3. 測る組を作り方ごとに束ね、束ごとにスクラッチのオブジェクトを 1 つ作る
4. 負の対照を 1 回書き、判定が効く項目だけを先へ進める
5. 現在値を在庫の中に見つけ、そこから上下へ 1 件ずつ広げる
6. 境界拡張が拾えなかったラベルを、項目ごとに残らず試す
7. 束を測り終えたらスクラッチのオブジェクトを削除し、次の束へ移る

### 対象は選択肢の形を受け取る 4 種である

`select` / `combo` / `mask` / `figure` を集める。**この 4 種は書かれた値を候補の
集合に対して解決する種別であり、解決できなければ拒む。** 判定に使えるのはこの
性質である。

**完全一致で照合される種別とは別の切り口である。** 書き戻し照合が完全一致を使う
種別はこれより広く、`text` や `file` も含む——`text` は任意の文字列を受け取るため、
受理されたことが所属の証明にならない。

`combo` はリストと文字の複合だが任意の文字列を受け取るわけではなく、
`図形 / 図形の種類` へ実在しない図形を書けば失敗し、`四角形` は受理される。

### 表へ入るのは在庫のラベルだけである

`図形の種類` の候補は「組み込みの図形 ∪ データディレクトリの svg」だが、**表へ
入るのは前者だけになる。**

| 部分 | 出所 | 在庫に現れるか |
|---|---|---|
| 組み込みの図形（`円` `四角形` `三角形` `五角形` `六角形` `星型` `ハート`） | ホストの内部 | **在る**（訳語を持つため） |
| svg ファイル | データディレクトリ | **無い**（訳す対象ではない） |

在庫の外は試さない。**加えて、走査を始めた時点でその項目が持っていた値も、在庫に
無ければ落とす。** 試して受理されたわけではない値がここから紛れ込む——
`縁取り / パターン画像` の既定値は空文字列であり、`図形の種類` は svg のファイル名を
取り得る。**落とさなければ表は環境ごとに違うものになる。**

この 2 つによって、利用者ごとに変わる値が表へ入る経路が無くなる。ファイル由来の
候補は表ではなく項目の説明が述べる——`図形の種類` の説明は「ボタンクリックでsvg
ファイルを選択出来ます」を含む。

### 判定が効くことを項目ごとに確かめる

解決できない値を拒むことを実測したのは `combo` 2 件（`図形 / 図形の種類` と
`縁取り / パターン画像`）だけであり、**4 種の全項目が同じ振る舞いをするとは測って
いない。**

そこで在庫を総当たりする前に、**候補になり得ない文字列を 1 回書く**（負の対照）。
その文字列は `=` を含む——在庫は `名前=訳語` の行から `=` の手前を取るため、
**在庫のラベルには成り得ない。**

| 対照の結果 | 意味 | 続き |
|---|---|---|
| 拒まれた | その項目は値を集合に対して解決している | 在庫を総当たりする |
| 受理された | 解決していない。受理は所属を意味しない | **在庫を試さずに報告へ回す** |

**`mask` と `figure` は実機で候補を起こしたことがまだ無い。** 在庫には組み込みの
図形のラベルが在るが、それが `figure` 型・`mask` 型の項目の選択肢として受理される
かは測っていない（`図形の種類` は `combo` である）。覆えなければ「在庫が覆って
おらず…」として報告へ落ちるだけであり、誤った候補が表へ入ることはない。

## 書き込み 1 回の費用は timeline の中身が決める

**ホストは編集のたびにプレビューを描き直し、そのフレームに乗るオブジェクトを
全て通す。** 描画はホストのメインスレッドを占有するため、その間 plugin は
生存確認の ping を返せない。描画が server の解決フェーズ予算（5 秒）を超えると、
生きているインスタンスが `instance_stale` として扱われ、走査はそこで落ちる。

したがって、**timeline に乗っているオブジェクトの数がそのまま完走の可否になる。**

| 何が乗っているか | 1 編集あたりの描画 |
|---|---|
| スクラッチ 1 つ | 数ミリ秒 |
| スクラッチ 147 個（対象の効果ごとに 1 つ） | **数秒。走査が進むほど伸びる** |

そこで生成器は走査を**オブジェクトの作り方で束ね**、束ごとに「作る → その上に
乗る (効果, 項目) を全て測る → 消す」を回す。**同時に生きるスクラッチは常に
1 つであり、1 編集あたりの費用は走査の総量に依らない。** 片付けも同じ形から
出る——途中で落ちてもプロジェクトへ残るのは高々 1 つである。

**空のプロジェクトで走らせるのはこのためである。** 既存のオブジェクトはスクラッチ
より先に描画へ乗り、しかも生成器には消せない。重い効果を持つプロジェクトを開いた
まま走らせれば、スクラッチが 1 つでも予算を超え得る。

`budget_scale_percent`（`%LOCALAPPDATA%\AviUtl2Mcp\settings.json`）を上げる必要は
無い。**空のプロジェクトなら既定の 100 で完走する。**

## 値域をどう起こすか

**書き戻し照合がそのまま測定器になる。** ホストは値域を外れた値を端へ倒し、桁の
多い小数を項目の桁へ丸める。倒された値は書き込みの失敗の応答に
`observed_value` として載るため、**倒された値そのものが値域である。**

| 探り | 得られるもの |
|---|---|
| 大きい値（200 万） | 上限 |
| 小さい値（-200 万） | 下限 |
| 小数を多く持つ値（`0.123456789`） | 小数桁 |

**小数桁は 3 回の探りが返した表記を突き合わせて決める。** 値域の内側へ収まった
探りはホストが項目の桁へ丸めた値を返すが、**端へ倒された値をホストが何桁で書き
出すかは測っていない。** 1 つの表記だけを根拠にすると、クランプの表記が桁を落として
いる場合に誤った小数桁が黙って表へ入る。桁が食い違ったら測れていないものとして
扱い、`decimals` を書かない。

小数桁の探りは `number` にだけ掛ける。**整数の項目へは小数を持つ値を書く形が
無い。**

### 探りの大きさはホストの表現の幅で決まる

**ホストは値を、項目の小数桁で目盛った 32 ビット整数として持つ。** 実測がこの形を
指す。

| 項目 | 小数桁 | 探り | 返った値 |
|---|---|---|---|
| `標準描画 / 拡大率` | 3 | 2,000,000 | `10000.000`（上限） |
| `標準描画 / 拡大率` | 3 | 20,000,000 | **`0.000`** |
| `標準描画 / X` | 2 | 20,000,000 | `100000.00`（上限） |
| `標準描画 / X` | 2 | 100,000,000 | **`0.00`** |

境目はどちらも「探り × 10^小数桁 が 2^31 に収まるか」に一致する。**幅を超えた
探りは端へ倒れず、巻き戻った値が `observed_value` に載る。** それは端ではない。

そこで探りは 200 万とする。小数 3 桁の項目まで幅に収まり（2,000,000 × 1000 <
2^31）、設定項目が取り得る大きさ（`サイズ` の上限が 4000、`拡大率` が 10000、
座標が 100000）より 1 桁以上大きい。`integer` と `number` で別に決める理由は
無い——**幅を決めるのは種別ではなく小数桁である。**

それでも幅を超えた観測（小数 4 桁以上の項目）は、返った表記の桁から判る。
**端としては読まず、報告へ回す。**

## 出力の読み方

- 効果名と項目名は昇順に並ぶ。差分が読めるようにするためである
- 葉は面の組である。**軸（効果名・項目名）と内容（`choices` / `range`）で階層が
  分かれる**ため、面が増えてもトップレベルのキーは増えない
- 候補の並びは**在庫の並び順**を保つ。ソートしない
- **候補は在庫のラベルだけである。** 走査を始めた時点の値も、在庫に無ければ表へは
  入らない
- **在庫から重複排除で消えたラベルの位置は正しくない。** 他の効果名や項目名と綴りが
  同じラベル（`合成モード` の `輝度` など）は在庫では選択肢の帯の外に 1 度だけ現れ、
  その位置に並ぶ。ホストの並びとは違う
- **値域は測れた欄だけを持つ。** 探りの値が値域の内側へ収まった側は測れない——
  受理されたことが言うのは「端が探りの外にある」ことだけであり、端が無いことの
  証明にはならない。上限だけを測れた項目は `max` だけを持つ
- **覆えなかった項目は表に入らない。** 実行の最後に理由付きで一覧する
  - 候補: 在庫の中で 1 件しか確認できなかった項目と、負の対照を受理した項目。
    前者にはプラグインが提供する効果が落ちる——その候補はプラグイン作者が
    サイドカーで配る。後者は判定が効いていないという観測である
  - 値域: 上限も下限も小数桁も測れなかった項目、探りがホストの表現の幅を超えて
    巻き戻った項目、ホストが返した値を数として読めなかった項目、探りが
    `item_value_not_applied` 以外で失敗した項目。移動を持つ項目
    （`track_movement_present`）が最後にあたる。
    **黙って値域を持たない項目にはしない**

## 実機なしで確かめられること

生成器はテストを持たない。そのぶん、**判定と組み立ての部分は実機を要さない形で
切り出し、モジュールとして読み込めるようにしてある。** 走査が始まるのは
`generate.mjs` を直接実行したときだけであり、`import` しても AviUtl2 へは触れない。

| export | 実機なしで確かめられること |
|---|---|
| `buildDocument` | 葉が面の組であること、効果名と項目名が昇順であること |
| `inInventoryOrder` | 在庫の外の値（空文字列、svg のファイル名）が落ちること |
| `rangeFacet` | 測れた欄だけが載ること |
| `fractionDigits` / `observedNumber` | 表記の読み取りと、読めない表記を弾くこと |
| `probeFitsHostScale` | 探りがホストの表現の幅に収まるかの判定 |
| `groupBySource` | 測る組が作り方ごとに束ねられ、束の並びも束の中の並びも走査の順に従うこと |
| `measureRange` / `WRITE` | 探りの結末を並べた差し替え可能な書き込み先を渡して、小数桁の突き合わせ・書き込み回数の数え方を確かめられる |

# 移動方法の可否の生成器

`crates/plugin/data/movement_facets.json` を、同じく起動中の AviUtl2 への書き込み
検証で起こす。plugin はこの JSON も `include_str!` でバイナリへ取り込む。

**一覧に載るのに書けない移動方法がある。** `aviutl2.ini` に登録されていて名前と
しては正しく、書き込みも発行されるが、読み直しがその移動を失う。移動を消す正解は
移動方法を指定しない指定（`mode` を `null`）である。**名前をコードへ埋め込まず、
走査で起こす**——移動方法の集合は環境ごとに違い、同じ性質の名前が他に無いとは
言えない。

## 前提

- **AviUtl2 が起動していること。** 作業ツリーのビルドを配置した状態で 1 つだけ
  立てる。開発用の配置は `target/debug` への symlink であり、**AviUtl2 の起動中は
  ビルドが失敗する**——先にビルドし、それから起動する。
- **`crates/plugin/data/movement_facets.json` が空であること。**
  → [走らせ直すときは表を空へ戻す](#走らせ直すときは表を空へ戻す)
- **空のプロジェクトが開いていること。** 生成器はスクラッチのオブジェクトを 1 つ
  作り、その上の 1 項目へ移動を書いては消す。**既存のオブジェクトには触れないが、
  プロジェクトは編集済みになる。** 保存しないこと。
- **`target/release` か `target/debug` に `aviutl2-mcp-server.exe` があること。**
  release を先に探す。
- **Node.js。** 標準ライブラリだけで動く。依存パッケージは無い。

## 使い方

```
node tools/effect-choices/movements.mjs
```

| 引数 | 既定 | 内容 |
|---|---|---|
| `--out <path>` | `crates/plugin/data/movement_facets.json` | 書き出し先 |
| `--server <path>` | `target/release` → `target/debug` | MCP サーバーの実行ファイル |

**走査は数十秒で終わる。** 1 名前あたりの書き込みは 2 回——移動を消す 1 回と、
測る 1 回である。これに、移動を失った名前を確かめ直す分（1 件あたり 2 回）と、
中間点を足す 1 回が加わる。13 件のうち 1 件が確かめ直しへ回るなら 29 回である。
進み方は `<移動方法の名前>: 書ける` の行で追える。

**`--out` を逸らしても、空であることは
`crates/plugin/data/movement_facets.json` について要求される。** 配置されている
plugin が読むのは、そのファイルから焼き込まれた表だからである。

## 何を測るか

**判定基準は「読み直しが移動を失うこと」である。** 書き込み検証が既に行っている
照合そのものであり、新しい規則を書かない。

1. `標準描画` を載せたオブジェクトを 1 つ作る。**作り方は決め打ちしない**——
   オブジェクトを作れる効果を順に試し、`標準描画 / X` が付いてきた最初の 1 つを
   使う
2. **移動方法の名前を引く。** 一覧を返す読み取りは無い。一覧に無い名前を書くと、
   失敗の `details.known_movements` にその環境の全件が並ぶ。**この失敗は書き込みを
   発行しない。** 値の個数の検証が名前の検証より先に来るため、区間の数を読んでから
   送る
3. 名前ごとに、まず移動を消して静的な値へ戻し、それから移動を書く。値は区間の
   境界ごとに `0` と `100` を交互に置く——**同じ値を並べると、移動が消えたのか
   保たれたのかを読み直しから見分けられない**
4. **移動を失った名前だけを、区間の数を変えて測り直す**（→[「書けない」は 2 回の
   観測で確かめる](#書けないは-2-回の観測で確かめる)）
5. 測り終えたらスクラッチのオブジェクトを消す

**測る前に移動を消すのは、判定の土台を名前ごとに変えないためである。** 書ける名前を
測った後はその移動が残る。移動を持つ状態から測ると、ホストが書き込みを無視して前の
移動を保った場合に「移動を失っていない」と読め、書けない名前が表から落ちる。静的な
値から測れば、ホストが値を捨てても無視しても、読み直しは単一の数値になる。

| 結末 | 記録 |
|---|---|
| 受理された | `writable: true` |
| `item_value_not_applied` で落ち、`observed_value` が区切りを持たない単一の数値 | **確かめ直しへ回す。** 両方で失えば `writable: false` |
| `item_value_not_applied` で落ちたが `observed_value` が移動を持つ | **表に載せず報告へ回す。** 違うのは値かパラメータであって移動の有無ではない |
| `track_mode_not_writable` で落ちた | **表に載せず報告へ回す。** 配置されている plugin が読む表が既にこの名前を書けないと述べている |
| 測る土台を作れなかった（移動を消せなかった） | **表に載せず報告へ回す** |
| 測定が例外で落ちた | **表に載せず報告へ回す。** 走査は次の名前へ進む |
| それ以外の失敗 | **表に載せず報告へ回す** |

**読めない表記も「移動を持つ」側へ倒す。** `writable: false` と名乗るには移動が
失われたという観測が要り、数として読めない表記はその観測にならない。

### 「書けない」は 2 回の観測で確かめる

**`writable: false` はバイナリへ焼き込まれ、以後その名前は全オブジェクトで拒まれ
る。** 1 回の観測では 2 つの誤りを分けられない——その 1 回だけホストが書き込みを
無視した場合と、**区間の境界より多くの制御点を要する移動方法**の場合である。
生成器が送れるのは常に「区間数 + 1」個であり、それ以外は書き込みの検証が拒む。
後者を焼き込めば、区間が多いオブジェクトでなら書けた名前が全域で拒まれる。

そこで 1 回目で移動を失った名前だけを、**スクラッチへ中間点を 1 つ足してから**
測り直す。中間点を足すのは走査を通して 1 度だけであり、**同時に生きるスクラッチは
1 つのままである。**

| 2 回目 | 記録 |
|---|---|
| また移動を失った | `writable: false` |
| 失わなかった | **表に載せず報告へ回す。** 区間の数で結果が変わる性質を、名前の表には書けない |
| 測れなかった | **表に載せず報告へ回す** |

**受理された側は補強を要さない。** 書き戻し照合が値・移動方法・フラグ整数の構造
一致を要求するためである。1 回目で `writable: true` になった名前は測り直さない。

### 1 件の失敗で走査は止まらない

名前 1 件の測定は例外まで含めて畳まれ、落ちた名前は理由付きで報告へ回る。ホストは
移動のパラメータを補って fingerprint を変えるため、追従しきれずに落ちる経路が実在
する。**走査ごと止めれば、書き出しは走査の後にあるためそれまでに測った全件が失わ
れる。**

走査を止める（非ゼロ終了する）のは、測定を 1 件も始められないときだけである——
表が空でない、`標準描画 / X` を載せたオブジェクトを作れない、移動方法の一覧を
引けない。

## 出力の読み方

- 名前は昇順に並ぶ。差分が読めるようにするためである
- **`writable` は真偽値であり、省略も `null` も無い。**「測っていない」を表す形は
  表に無い
- **覆えなかった名前は表に入らない。** 実行の最後に理由付きで一覧する。表に無い
  名前は plugin の側で書ける側になる
- **一覧が 32 件ちょうどで返ったら、その先は届いていない可能性がある。** 失敗の
  応答は配列をその件数で切る。生成器はこのとき警告を出すが、切られた分の名前は
  受け取っていないため報告にも並ばない

## 走らせ直すときは表を空へ戻す

**表が既に埋まっていると測れない。** plugin は表を読み、書けないと述べている名前
への書き込みを発行の前に拒む（`track_mode_not_writable`）。その状態で走らせれば、
走査は自分の前回の出力を写すだけになる。

そこで生成器は、`crates/plugin/data/movement_facets.json` が空でなければ走査を
始めずに落ちる。**迂回する引数は無い。**

```json
{
  "movements": {}
}
```

へ戻し、plugin をビルドし直してから走らせ直す。**配置されている plugin が作業
ツリーのビルドでなければ、表を空にしても `track_mode_not_writable` が返る**——
その名前は表に載らず、報告に表が古い可能性として並ぶ。

## 実機なしで確かめられること

判定と組み立ては実機を要さない形で切り出してある。走査が始まるのは
`movements.mjs` を直接実行したときだけであり、`import` しても AviUtl2 へは触れ
ない。

| export | 実機なしで確かめられること |
|---|---|
| `observedHasMovement` | 単一の数値だけが移動を失った値であること。読めない表記を「失った」側へ倒さないこと |
| `lostMovement` | 確かめ直しへ回す結末がどれか |
| `verdict` / `WRITE` | 1 回目と 2 回目の結末の組が `true` / `false` / 表に載せない（理由付き）のどれになるか。理由を名乗らない失敗が `undefined` と綴られないこと |
| `buildDocument` | 名前が昇順であること、載せないと決めた名前が現れないこと、`writable` が真偽値であること |
| `tableIsEmpty` | 空の表と、空でない表・読めない表の区別 |

**結末の振り分けは `verdict` 1 か所に集めてある。** 測定の側は結末を組み立てる
だけで、表への載せ方を決めない。

検査は `tools/effect-choices/movements.test.mjs` にある。Node の標準テスト
ランナーで走らせる。

```
node --test tools/effect-choices/*.test.mjs
```

**`cargo test` からは走らない。** このディレクトリはワークスペースの外にあり、
製品のビルドにも lint にも関与しない。
